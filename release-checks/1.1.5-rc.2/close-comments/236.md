Fixed in **1.1.5-rc.2** (QA channel) by #237 (merge 8391df8; release commit 120b2f0).

**Root cause** (details in #237): #220 removed the start-up screen's wait for the warm runtime, so the entry session took the only runtime while it was still starting and the first New session had to start its own (2–8 s). #237 restores the start-up wait (UI) and has the warm pool report `starting` instead of `off` while a session attaches to the runtime it took (host).

**Verified on 1.1.5-rc.2**, Windows 11 x64, installed QA build upgraded in place from 1.1.5-rc.1, isolated data dirs:
- By hand, 3 of 3: the start-up screen stays until the runtime is ready; New session right after it, Send, then Stop returns to idle in 163–280 ms, and the next message is answered.
- Abnormal playbook "Stop right after Send" in the full run: passes (1.1.5-rc.1 failed 5 of 7).
- Host test `the_pool_reads_starting_while_a_session_attaches_until_the_next_is_ready` and e2e `send-while-starting` pass in CI for the release commit.

**Regression scenario:** e2e `send-while-starting` (start-up screen waits, the first New session after it is ready at once) and the abnormal playbook case "Stop right after Send".

Not covered here: when Stop lands after the runtime has recorded the model request but before handing it off, the next message is held by Flow. That is a runtime issue, tracked in #145.
